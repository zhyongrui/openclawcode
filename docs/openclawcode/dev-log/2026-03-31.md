# 2026-03-31

This log records two ClaudeCode-inspired adaptation slices that were pushed
forward in `openclawcode` today:

1. detached-session provenance for background ACP work
2. runtime tool-surface assembly visibility

The intent was not to clone ClaudeCode internals. The intent was to move
selected product and operator-facing patterns onto `openclawcode`'s existing
runtime model.

## What shipped

### 1. Detached/background task provenance became durable and inspectable

The task and flow model now keeps enough metadata to distinguish work that was
spawned as a detached ACP/background session from ordinary foreground activity.

Implemented behavior:

- `TaskRecord` and `FlowRecord` carry `originKind` and `originSessionKey`
- ACP-created detached runs stamp `originKind: "detached_session"`
- SQLite-backed task and flow stores preserve that metadata
- `tasks` and `flows` operator commands now show origin details
- detached ACP work defaults to the clearer operator-facing label
  `"Detached ACP session"`

This is the substrate needed before adding a first-class "background the
current foreground session" UX.

### 2. Effective tool resolution now exposes one runtime assembly summary

Borrowing from ClaudeCode's "single assembly layer" idea, the effective tool
path now has an explicit assembly stage instead of only returning grouped tool
lists.

Implemented behavior:

- `resolveEffectiveToolSurface(...)` now resolves:
  - workspace and agent directories
  - the effective tool set
  - grouped inventory output
  - one structured `assembly` summary
- `assembly` reports:
  - counts by source: `core`, `plugin`, `channel`, `total`
  - runtime context: channel provider, model provider/model id, reply mode,
    owner context
  - runtime flags: subagent binding allowance, explicit-target requirement,
    message-tool disablement
- `tools.effective` now returns that assembly metadata through the gateway
  schema
- `/tools` now renders a `Runtime:` line so operators can see which runtime
  context produced the visible tool surface

This does not yet add a full rollout dashboard or a "why hidden" explanation
surface, but it establishes a concrete boundary for that future work.

## Follow-up

The next ClaudeCode borrowing steps should build on these narrower substrates
instead of jumping straight to a large opaque feature port:

- add a user-facing "background this session" affordance on top of the new
  detached-session provenance model
- add a clearer operator explanation surface for why a tool is denied,
  gated, or profile-filtered
- keep the borrowing docs updated with explicit implementation status so the
  repo distinguishes "analyzed", "adapted", and "not started"
