# 2026-03-29

Feishu operator discovery moved from an OAuth/QR-heavy direction to a simpler
two-path product model:

1. contact lookup first
2. scan bot and send code as fallback

This log summarizes the user-facing functionality that shipped across the
related Feishu setup and runtime changes.

## What shipped

### 1. Contact lookup became the primary operator-discovery path

OpenClaw Code can now discover the intended Feishu operator from either:

- work email
- mobile number

The flow now supports:

1. collecting the operator contact in onboarding
2. resolving the Feishu `open_id` from that contact
3. persisting `user:<open_id>` as the preferred operator target
4. writing the Feishu allowlist entry needed for follow-up setup
5. sending the first proactive welcome/setup message

This replaced the earlier assumption that operator discovery should primarily
depend on QR claim URLs.

### 2. Feishu onboarding copy was redesigned around user intent

The setup surface no longer frames this step as an internal "binding"
ritual. The prompt is now:

```text
How should we find you on Feishu?
● Work email (Recommended)
○ Mobile number
○ Scan bot and send code
○ Skip for now
```

The surrounding setup copy was aligned to stay in English on that surface and
to avoid mentioning `openclawcode` where the user only needs to decide how
OpenClaw should identify them on Feishu.

### 3. Credential guidance was corrected for contact lookup

The Feishu credential help shown during onboarding now lists the additional
permission required for contact-based lookup:

- `contact:user.id:readonly`

The full expected permission list for this slice is now:

- `im:message`
- `im:chat`
- `contact:user.base:readonly`
- `contact:user.id:readonly`

### 4. The old QR OAuth/public-callback operator-binding path was removed

The earlier Feishu operator-binding direction depended on:

- QR claim URLs
- public callback routing
- temporary tunnel/public URL logic
- OAuth callback handling

That path is no longer the active product flow for operator discovery. The
surface was simplified to:

- contact lookup first
- message-driven scan fallback second

This removed the need to treat temporary public callback URLs as part of the
normal operator-setup story.

### 5. Scan bot and send code was implemented as the fallback path

The fallback now works as a delayed runtime flow instead of an onboarding-time
QR claim:

1. onboarding records that the operator chose scan fallback
2. onboarding does not immediately ask the user to send a code
3. Gateway starts
4. the Feishu transport becomes ready
5. OpenClaw shows the bot QR code plus a short one-time code
6. the operator opens the bot and sends that code in a direct message
7. OpenClaw uses the real message event to identify the sender `open_id`
8. OpenClaw persists that user as the preferred operator target
9. OpenClaw sends the first proactive welcome message

This keeps the fallback message-event-driven and avoids public OAuth callback
requirements.

### 6. Scan code display was moved to the correct runtime moment

The scan fallback no longer tries to show a QR/code while the system is still
mid-onboarding and not yet able to receive Feishu messages reliably.

The delivered behavior is:

- the QR/code is deferred until Gateway and Feishu are actually ready
- the scan/code panel is shown after the `Token` note and before
  `How do you want to hatch your bot?`
- onboarding blocks until the scan/code surface is actually available instead
  of silently finishing too early

This fixed the earlier product gap where the user could be asked to act before
the message receiver was online.

### 7. Scan-code claims now complete directly in the Feishu channel runtime

The final scan-code implementation no longer depends on a fragile indirect hook
path for the actual claim/finish behavior.

When a direct Feishu DM contains the current valid one-time code, the runtime
now completes the critical path directly:

1. claim the pending one-time code
2. persist the preferred Feishu operator target
3. add the allowlist entry
4. suppress the old generic pairing guidance reply
5. send the proactive welcome message

This made the fallback deterministic and much easier to reason about in real
runtime logs.

### 8. Scan-code matching was hardened for real user messages

The matcher no longer requires the user to send only the bare code.

It now accepts messages that contain the active code after normalization, so
these kinds of inputs can be recognized:

- `CY2JXH`
- `my code is CY2JXH`
- messages containing separators or light punctuation around the code

This removed a real-world failure mode where the user sent the correct code in
natural language but the system treated it as a mismatch.

### 9. The failure path no longer falls back silently

If scan-code matching fails, the user now gets an explicit reply instead of a
silent no-op or an accidental fallback into the older pairing behavior.

This made it clear whether:

- the code was wrong
- the code had expired
- the message was unrelated

instead of making the chat appear dead.

### 10. Re-running onboarding after a successful bind is now handled cleanly

Once a Feishu operator target already exists, onboarding no longer waits for a
new scan code that will never be generated.

Instead, it now reports in English that:

- a Feishu operator is already configured
- scan-and-code is being skipped
- the existing target must be cleared first if the operator wants to test the
  fallback again

This removed the confusing 60-second timeout after a successful prior bind.

### 11. The stale `memory` CLI command entry was removed

During the same slice, the repo-local CLI build was fixed by removing a stale
dynamic import reference to a deleted `memory-cli.js` entry in the command
registry.

That cleared a real build blocker and restored `pnpm build` for the local
checkout used during Feishu testing.

## Notable runtime fixes made along the way

- source-plugin runtime resolution was aligned so local source plugins no
  longer mixed with an older global runtime
- Feishu scan-code state was unified onto the canonical OpenClaw state dir so
  onboarding and runtime read the same pending-code store
- the default pairing help reply was suppressed for successful scan-code claims
- temporary debug logging was later removed after the claim path stabilized

## Current delivered product shape

After this work, the intended Feishu operator-discovery story is:

1. use work email first
2. use mobile number when email is not suitable
3. use scan bot and send code as the fallback
4. do not depend on QR OAuth/public callback hosting for the normal operator
   setup path
